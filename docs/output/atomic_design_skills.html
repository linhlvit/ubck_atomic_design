LLD · Quy tắc attribute

Pattern thiết kế Attribute

FK → Fundamental entity
Luôn tạo cặp: [Entity] Id (Surrogate Key) + [Entity] Code (Text). Kể cả khi nullable. Id = FK constraint. Code = denormalized lookup.
Classification Value
Chỉ 1 trường [...] Code (domain = Classification Value). KHÔNG tạo cặp Id + Code. Áp dụng cả cho Currency, Calendar Date.
Data Domain — ngữ nghĩa ưu tiên
Chọn domain theo ý nghĩa nghiệp vụ, không ép theo data type nguồn. Ghi conversion risk vào comment nếu domain ≠ data type nguồn.
Source System Code
Mô tả đến mức bảng nguồn: DCST.THONG_TIN_DK_THUE, không chỉ ghi DCST. Format fully qualified: SOURCE.schema.Table.Column.
FK comment syntax
FK target: EntityName.Entity Id. cho Id.
Lookup pair: EntityName.Entity Code. Pair with {Id}. cho Code. Currency Code dùng FK target:.
Technical fields
Tất cả technical fields có prefix ds_. KHÔNG thiết kế ds_* trong file attr_*.csv — script aggregate tự thêm.

Quy tắc cốt lõi

11 Core Design Rules

R1 · Grain
Xác định rõ grain cho mỗi bảng — mỗi dòng đại diện cho gì. Grain sai → mọi thứ sai theo.
R2 · Surrogate Key
Luôn tạo surrogate key trên Atomic. Không dùng @ID T24 làm PK. T24 @ID → Business Key (BK).
R3 · Pattern Id + Code
FK đến Fundamental entity → cặp [Entity] Id (Surrogate Key, dùng join) + [Entity] Code (Text, lưu dư thừa).
R4 · Classification Value
Chỉ 1 trường Code (domain = Classification Value). Không tạo cặp Id + Code. Tương tự cho Currency.
R5 · Technical prefix ds_
Tất cả technical fields trên Atomic có prefix ds_. Không thiết kế thủ công — script tự thêm.
R6 · BCV — bắt buộc tra cứu
Không suy luận BCV Concept từ tên bảng. Grep knowledge/terms.csv trước. Cấu trúc trường quyết định concept.
R7 · Đặt tên entity
Pattern: [Domain Prefix] + [BCV Term]. Tất cả entity cùng nhóm nghiệp vụ phải chung prefix.
R8 · Entity con ⊃ tên cha
Tên entity cha phải là substring liên tục trong tên entity con. VD: Fund → Fund NAV, không phải NAV Record.
Quy tắc cốt lõi (tiếp)

Thêm 3 Rules quan trọng

R9 · Condition vs Transaction
Biểu phí / quy định = [Condition] — định nghĩa mức phí, tỷ lệ, điều khoản áp dụng chung.
Phí thực tế phát sinh từng hồ sơ = [Event] Transaction — ghi nhận từng lần thực tế thu/chi phí.
Nhầm 2 loại này → sai grain + sai table type toàn bộ entity nhóm phí.
R10 · Gộp entity khi hợp lý
Cấu trúc tương tự + ít trường → gộp, dùng Classification Value phân biệt. Tránh proliferation entity không cần thiết.
R11 · Entity concept vs Reference data set
Bảng chỉ có Code + Name, không có instance data → Classification Value (reference data set), không phải Atomic entity.
Ngoại lệ: Geographic Area (tỉnh/thành phố/quốc gia) dù chỉ Code + Name → vẫn là Atomic entity [Location].
Cảnh báo

8 Lỗi phổ biến

01 Dùng @ID T24 làm PK Atomic — không tạo surrogate key.
02 Không lọc RECORD.STATUS = 'LIVE' → lẫn dữ liệu UNAUTH/RNAU chưa authorize.
03 Gán BCV Concept sai do không tra cứu knowledge/ — chỉ đoán từ tên bảng.
04 Nhầm reference data set (Classification Value) với entity concept → tạo Atomic entity thừa.
05 Entity con đặt tên không chứa đầy đủ tên entity cha (vi phạm R8).
06 Thiếu prefix hoặc prefix không nhất quán trong nhóm entity cùng nghiệp vụ.
07 Nhầm Condition và Transaction cho nghiệp vụ phí — sai grain + table type toàn nhóm.
08 Nhầm vai trò Atomic và Gold → đặt logic khai thác / aggregation vào tầng Atomic.

Vì sao dùng Skill

AI Reasoning — không thể thay bằng checklist

BCV Assignment — tra cứu chưa đủ
Grep knowledge/terms.csv chỉ cho candidate. AI phải đọc cấu trúc cột → hỏi "entity này thực ra mô tả cái gì?" → đối chiếu term → ra quyết định có lập luận. VD: INVESTOR_RATING → grep ra category Group nhưng concept thực là [Involved Party].
Entity concept vs Reference data set
Rule R11 có exception: Geographic Area dù chỉ Code + Name → vẫn là Atomic entity [Location] vì BCV có Data Concept riêng. Exception không list hết được — mỗi source phải đọc, tra BCV, rồi phán xét.
Condition vs Transaction — cùng domain "phí"
Không có trường kỹ thuật nào phân biệt. AI phải hỏi: "Bảng này định nghĩa quy tắc hay ghi nhận occurrence?" Cùng có trường "phí giao dịch" — một bảng là Condition, một bảng là Fact Append. Checklist không phân biệt được.
Pure junction — threshold judgment
Junction có attribute nghiệp vụ riêng → tạo entity; không có → denormalize ARRAY. Nhưng không có quy tắc cứng "bao nhiêu trường là đủ". Một trường effective_date hay is_primary có thể đủ để đổi quyết định — AI phải xét ngữ nghĩa.
Grain judgment — shared entity
Cùng có trường địa chỉ: COMPANY_PROFILE (grain = 1 công ty → tách IP Postal) vs QUARTERLY_REPORT_ADDRESS (grain = 1 báo cáo → giữ denormalized). Hai bảng, kết quả ngược nhau hoàn toàn — checklist không phân biệt.
Circular reference trong Tier
2 entity FK lẫn nhau → giữ cùng Tier, ghi điểm xác nhận. Không tách thêm Tier chỉ để tránh circular — tách sai về mặt conceptual. AI phải nhận ra circular, hiểu tradeoff, và giải thích được lý do giữ nguyên.

📄 CSV → YAML

Git-friendly — YAML diff rõ ràng từng attribute thay đổi, không bị "1 dòng CSV thay đổi toàn bộ"
Nested schema — biểu diễn trực tiếp cặp Id + Code, Array<Struct>, classification_context mà không cần encode vào 1 cột flat
Linh hoạt schema — thêm field mới (conversion_risk, propose_domain...) không phá vỡ file cũ
Ví dụ — attribute hiện tại (CSV flat):
Fund Id,Khóa surrogate,Surrogate Key,false,false,...
→ YAML nested:

  domain: Surrogate Key
  nullable: false
  fk_target: Fund.Fund Id
